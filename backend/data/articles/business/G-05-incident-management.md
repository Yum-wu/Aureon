# 事件管理：从告警到复盘

## 事件管理流程

### 生命周期

```
检测 → 响应 → 缓解 → 解决 → 复盘
```

### 严重级别

| 级别 | 定义 | 响应时间 | 示例 |
|------|------|---------|------|
| P0 | 全面服务中断 | 5 分钟 | 数据库宕机 |
| P1 | 核心功能受损 | 15 分钟 | RAG 查询超时 |
| P2 | 部分功能降级 | 1 小时 | Rerank 服务不可用 |
| P3 | 轻微影响 | 4 小时 | 监控面板延迟 |

## 告警设计

### 告警原则

1. **可操作性**：每个告警都应有明确的处理步骤
2. **低噪声**：告警太多会导致告警疲劳
3. **分级**：不同严重级别不同通知渠道
4. **上下文**：告警应包含足够信息帮助定位

### 告警规则

```python
class AlertRule:
    """告警规则"""

    def __init__(self, metric: str, threshold: float, severity: str, duration: str):
        self.metric = metric
        self.threshold = threshold
        self.severity = severity
        self.duration = duration

# 示例告警规则
ALERT_RULES = [
    AlertRule("error_rate", 0.05, "P0", "5m"),    # 错误率 >5% 持续5分钟
    AlertRule("p99_latency_ms", 5000, "P1", "10m"), # P99延迟 >5s 持续10分钟
    AlertRule("qdrant_health", 0, "P1", "1m"),      # Qdrant 不健康
    AlertRule("disk_usage_pct", 90, "P2", "30m"),   # 磁盘使用 >90%
]
```

## 复盘文化

### 无指责复盘（Blameless Postmortem）

复盘的目标是**找出系统性问题**，而非追究个人责任。

### 复盘模板

```
## 事件概述
- 时间：2026-06-15 14:30 - 15:45（75 分钟）
- 影响：RAG 查询 P99 延迟从 2s 升至 15s，约 30% 用户受影响
- 严重级别：P1

## 时间线
- 14:30 告警触发：P99 延迟超过 5s
- 14:35 值班工程师开始调查
- 14:45 定位原因：DashScope Rerank API 限流
- 15:00 启用降级：跳过 Rerank，直接返回检索结果
- 15:30 DashScope API 恢复
- 15:45 关闭事件

## 根因分析
- 直接原因：DashScope Rerank API 限流
- 根本原因：未设置 Rerank 降级策略，API 限流时整个请求阻塞

## 行动项
1. [已完成] 添加 Rerank 降级策略（跳过 Rerank 直接返回）
2. [进行中] 添加 DashScope API 限流监控
3. [待办] 实现 Rerank 多供应商降级链
```

## 关键事实

1. **事件管理生命周期**：检测 → 响应 → 缓解 → 解决 → 复盘，每个阶段有明确的职责和流程
2. **P0 级别要求 5 分钟内响应**，P1 要求 15 分钟，P2 要求 1 小时，P3 要求 4 小时
3. **告警设计三原则**：可操作性（每个告警有处理步骤）、低噪声（避免告警疲劳）、分级（不同级别不同通知渠道）
4. **无指责复盘（Blameless Postmortem）**的目标是找出系统性问题，而非追究个人责任
5. **复盘的行动项必须跟踪到完成**，否则同样的故障会再次发生
