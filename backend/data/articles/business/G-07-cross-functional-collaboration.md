# 跨职能协作：产品-设计-工程高效配合

## 跨职能协作的挑战

产品、设计和工程三个职能有不同的思维方式和优先级，协作不畅是项目延期和质量问题的主因。

## 三职能角色

| 角色 | 关注点 | 思维方式 | 常见冲突 |
|------|--------|---------|---------|
| 产品 | 用户价值、商业目标 | What & Why | 功能太多，优先级不清 |
| 设计 | 用户体验、交互流程 | How it feels | 设计稿与实现差距大 |
| 工程 | 技术可行性、系统质量 | How it works | 需求变更频繁，技术债累积 |

## 协作框架

### 阶段一：对齐（Align）

产品、设计、工程共同参与需求讨论，确保三方理解一致：

```
产品：用户问题是什么？成功标准是什么？
设计：用户流程是什么？交互方案是什么？
工程：技术方案是什么？风险和约束是什么？
```

### 阶段二：共创（Co-create）

三方共同参与方案设计，而非串行交接：

```
❌ 串行：产品写 PRD → 设计出稿 → 工程实现
✅ 共创：三方讨论 → 产品写 PRD + 设计出稿 + 工程评估 → 迭代
```

### 阶段三：交付（Deliver）

使用敏捷方法，短迭代、快速反馈：

- Sprint 周期：2 周
- 每日站会：15 分钟，同步进度和阻碍
- Sprint Review：演示成果，收集反馈
- 回顾会：改进流程

### 阶段四：复盘（Reflect）

每个项目结束后复盘协作效果：

```
1. 什么做得好？
2. 什么可以改进？
3. 下次我们尝试什么？
```

## 沟通最佳实践

1. **单一信息源**：所有需求、设计、技术文档在一个地方
2. **异步优先**：文档 > 消息 > 会议
3. **决策记录**：记录每个决策的原因和参与者
4. **定期同步**：每周产品-设计-工程三方同步
5. **快速反馈**：设计评审和代码审查及时反馈

## 关键事实

1. **跨职能协作的核心挑战**是产品、设计、工程有不同的思维方式和优先级
2. **共创模式优于串行交接**——三方共同参与方案设计，而非产品写 PRD → 设计出稿 → 工程实现的串行流程
3. **单一信息源原则**：所有需求、设计、技术文档在一个地方，避免信息分散和版本不一致
4. **异步优先**：文档 > 消息 > 会议，减少不必要的同步会议
5. **决策记录**记录每个决策的原因和参与者，防止"为什么这样做"的知识流失
